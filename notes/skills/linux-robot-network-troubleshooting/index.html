Linux 机器人网络与端口排查

Linux 机器人网络与端口排查

Section titled “Linux 机器人网络与端口排查”

核心顺序

Section titled “核心顺序”

遇到“客户端连不上”时，按以下顺序查：

五组最小命令

Section titled “五组最小命令”

1. 进程

Section titled “1. 进程”

不要只看到 grep 自己就认为服务已运行。记录真正的 PID 和启动命令。

2. 监听端口

Section titled “2. 监听端口”
  • 没有输出：服务未启动、启动失败或监听了别的端口。
  • 监听 127.0.0.1:15701：只允许同一网络命名空间访问。
  • 监听 0.0.0.0:15701：允许从可达网卡访问，但仍受防火墙和路由影响。

3. 网卡与地址

Section titled “3. 网卡与地址”

Driver 启动参数中的 <networkInterface> 应指向连接机器人的真实网卡，不能凭名字猜 eth0。

4. HTTP 探针

Section titled “4. HTTP 探针”

curl -v 可以看到连接目标、HTTP 头和状态；若已收到 JSON-RPC 错误，说明网络和 HTTP 至少已走通。

5. Windows 与 WSL

Section titled “5. Windows 与 WSL”

先判断服务运行在哪里：

  • Windows Client → Windows 服务：通常使用 Windows 的 127.0.0.1。
  • WSL Client → WSL 服务：通常使用 WSL 的 127.0.0.1。
  • 跨 Windows/WSL：先确认服务监听地址和当前 WSL 网络模式，再用实际地址验证，不假设 localhost 一定跨边界可达。

^[inferred] 跨环境排障时，最重要的不是背一个固定 IP，而是先明确“请求从哪个网络命名空间发出、服务在哪个空间监听”。

典型现象与下一步

Section titled “典型现象与下一步”
现象最可能层下一步
Connection refused进程 / 端口查 ps、ss、URL 端口
连接超时路由 / 防火墙 / 服务阻塞查目标 IP、路由、服务日志
HTTP 404HTTP path核对 /mcp
收到 -32700JSON修请求体，不再查网卡
收到未知工具MCP先 tools/list
Driver 正常但机器人无响应网卡 / DDS / SDK / 实体查 Driver 网卡参数和现场状态

面试口述

Section titled “面试口述”

我先确认服务运行在哪个系统和网络空间，再查进程、监听端口、IP 与路由。随后用 curl 发送最小请求，把 Python Client 排除在外。能收到 JSON-RPC 返回就说明网络和 HTTP 已基本走通，再进入 MCP、Driver、DDS 和机器人状态层。

自测

Section titled “自测”
  • 能解释 ps、ss、ip address、ip route 各回答什么。
  • 能用 curl -v 独立于 Python 验证 /mcp。
  • 能区分 connection refused、timeout 和 HTTP 404。
  • 能说明为何不能写死网卡名或 WSL IP。
