curl 会根据选项自动选择方法：

-X/--request 只改请求行里的方法字符串，不会同步改变 curl 的发送行为。典型错误是用 -X HEAD：curl 仍可能按普通请求等待响应体；正确写法是 --head。

只有没有专用选项的方法（如 DELETE、PATCH 或 WebDAV 方法）才通常需要 --request：

固定 -X 后，curl 跟随重定向时还会继续使用该方法，因此更容易制造意外请求。

HTTP 状态不是 curl 退出码

Section titled “HTTP 状态不是 curl 退出码”

默认情况下，收到完整的 HTTP 404/500 仍可能退出 0：传输成功，但应用请求失败。

脚本里优先使用：

  • --fail-with-body：HTTP 400+ 时保留响应体，并返回退出码 22；需要 curl 7.76.0+。
  • --fail：也让 HTTP 400+ 非零退出，但隐藏响应体，兼容更早版本。
  • --silent 隐藏进度条；要与 --show-error 一起用，否则错误信息也会消失。

高频退出码：

退出码含义第一检查点
0curl 认为传输成功再看 HTTP 状态和业务响应
6无法解析主机名DNS、URL、引号
7无法连接目标服务、IP、端口、监听地址
22HTTP 错误，且启用了 fail 选项状态码和响应体
28超时路由、防火墙、服务阻塞、超时预算
35TLS 握手失败TLS 版本、代理、服务配置
60证书校验失败CA、证书链、域名、有效期

重定向、超时与重试

Section titled “重定向、超时与重试”
  • --location/-L 跟随重定向；不加时应直接检查 3xx 与 Location 头。
  • curl 默认不会把凭证转发给重定向后的其他主机。不要为“省事”启用 --location-trusted，它会扩大凭证泄露范围。
  • --connect-timeout 只限制连接阶段，--max-time 限制整个传输。
  • --retry 只针对超时和部分临时 HTTP 错误（如 408、429、500、502、503、504），不是“所有失败都重试”。
  • 对 POST/PATCH 等可能产生副作用的请求，不要盲目重试；只有 API 提供幂等键或能证明操作可安全重复时才这样做。
  • --retry-all-errors 可能重复发送或接收数据，不应作为全局默认值。

TLS 与敏感信息边界

Section titled “TLS 与敏感信息边界”
  • --insecure/-k 会关闭证书校验。它只能用于明确受控的临时诊断，不能进入生产脚本。
  • --verbose、trace、命令历史、CI 日志和截图都可能暴露 Authorization、Cookie 或请求体；分享前先脱敏。
  • 不要把真实 Token、密码或 Cookie 写进笔记、脚本示例和 shell 历史。
  • Basic Auth 需要长期使用时，可考虑权限受控的 --netrc-file；该文件仍是明文凭证，必须限制文件权限。

分层排障矩阵

Section titled “分层排障矩阵”
现象已证明什么下一步
Could not resolve host / code 6还没连到服务器查 URL、DNS、shell 引号
Connection refused / code 7主机可达但目标没有接受连接查进程、监听端口、地址
code 28 超时在规定时间内未完成查路由、防火墙、服务阻塞
code 60到了 TLS 校验阶段查 CA、证书链、域名与有效期
HTTP 404TCP/TLS/HTTP 已基本走通修 path，不再优先查网卡
HTTP 400/415服务收到请求但不接受格式查 JSON、Content-Type、schema
HTTP 401/403服务收到请求并进入认证/授权查 Token、权限、时钟与作用域
JSON-RPC/MCP 错误HTTP 层通常已走通查 method、params、工具 schema

完整的进程、端口、网卡和路由顺序见 Linux 机器人网络与端口排查；不要把每个错误都归因于“网络不通”。
