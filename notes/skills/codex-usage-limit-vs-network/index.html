Codex 用量超限与网络故障的鉴别

Section titled “Codex 用量超限与网络故障的鉴别”

适用症状：「Codex 一直在出网络问题」 —— 界面转圈很久、重试、然后弹错。 结论先行：Codex 报「网络问题」时，八成不是网络。 先读错误码字段，再决定查不查网络。 原始证据见 2026-09-10 诊断证据 · 未公开。 代理/传输层的前置知识见 Clash VPN 本机网络排障。

第一原则

Section titled “第一原则”

不要相信错误文案，要读错误码。

Codex 的超限错误在 UI 上表现为「请求失败 / 连接中断 / 请重试」，但在 session 日志里写得很清楚：

codex_error_info 是结构化的归因字段。先统计它，再动手查网络。

第二步：区分「挂起」和「断连」

Section titled “第二步：区分「挂起」和「断连」”

这是用户把配额问题误判成网络问题的根本机制。

实测：

现象更可能是
长时间挂起（分钟级）后弹错配额 / 服务端 —— 请求在排队、被限流重试
秒级立刻失败真网络 —— DNS、连接拒绝、TLS 失败
首字节延迟很大但最终成功节点质量差，不是故障

^[inferred] 判据：配额错误必然伴随长的 duration_ms，因为客户端在「排队 + 退避重试」而不是在传输。

第三步：核对配额真值

Section titled “第三步：核对配额真值”

配额不只在错误里，也周期性写在 session 里：

解读要点：

字段含义
primary短窗口（通常 300 分钟 = 5 小时）
secondary长窗口（通常 10080 分钟 = 7 天）—— 绑定约束通常是它
credits.balance附加额度余额，"0" 表示没有
常见比例短窗口重置快；长窗口到 90%+ 会持续撞墙直到重置

关键：短窗口重置 ≠ 恢复可用。短窗口清零而长窗口仍在 90%+ 时，会立刻再次触发 usage_limit_exceeded。

陷阱 A：测试工具的 TLS 指纹会骗你

Section titled “陷阱 A：测试工具的 TLS 指纹会骗你”

同一端点、同一节点、不同客户端，结果可能完全相反：

客户端https://chatgpt.com/
curl.exe200 ✅
PowerShell Invoke-WebRequest403（Cf-Mitigated: challenge）

Cloudflare 会按 TLS/HTTP 指纹下发人机验证。PowerShell 的 .NET 栈指纹很像机器人。 👉 判断节点能否用于 Codex，必须用 curl.exe（或直接看 Codex 日志），不要用 Invoke-WebRequest。

陷阱 B：先确认代理当前的 mode

Section titled “陷阱 B：先确认代理当前的 mode”

Clash 在 mode: global 时，所有流量走 GLOBAL 组，切换普通策略组（如「🔰 选择节点」）完全无效。

^[extracted] 本次第一轮 46 节点扫描因此全部测的是同一个节点，得出「所有节点同 IP」的错误结论。动节点前先确认 mode 和生效组。

Section titled “Codex 端点的可达性基线”
端点正常响应说明

Section titled “第六步：绕开配额的两条路”

方案做法代价
等 / 降用量等 7 天窗口重置；同时降 §4 的三个放大器0 成本

^[inferred] API key 路径的优势是双重的：绕过配额体系 + 绕开 chatgpt.com 的 Cloudflare 挑战。缺点是失去套餐内包含的额度。

自检清单

Section titled “自检清单”
  • 我先跑了 codex_error_info 统计，而不是先查网络。
  • 我区分了「分钟级挂起后弹错」和「秒级立刻失败」。
  • 我读了 rate_limits 的 primary 和 secondary，并换算了重置时间。
  • 我知道短窗口重置 ≠ 恢复可用。
  • 我检查了 config.toml 的三个用量放大器。
  • 判断节点时我用了 curl.exe 而不是 Invoke-WebRequest。
  • 动节点前我确认了 mode 与生效的 GLOBAL 组。
  • 我把 401 / 302 / 405 判为「通」，只把 403 + cf-ray 判为「被拦」。
