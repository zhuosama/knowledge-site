跨机器同步仓库的两类静默陷阱

跨机器同步仓库的两类静默陷阱

Section titled “跨机器同步仓库的两类静默陷阱”

当同一个 working tree 通过文件级同步器（Syncthing、Dropbox、iCloud）在 Windows 和 macOS 之间共享，并且该目录中包含调度自动化（launchd / cron / systemd）时，会出现两类独立的 bug——两者都 静默失败：任务继续”运行”，日志继续写入，仪表盘一切正常，但实际上没有任何工作完成。

陷阱 1：换行符污染（CRLF）

Section titled “陷阱 1：换行符污染（CRLF）”

机制

Section titled “机制”

Syncthing 同步的是 working copy 的原始字节，而非 Git 规范化后的 blob。如果 Windows 端设置了 core.autocrlf=true 且仓库缺少 .gitattributes：

  1. Windows 将工作副本写为 CRLF（\r\n）^[extracted]
  2. Syncthing 把这些 CRLF 的 shell 脚本传输到 Mac ^[extracted]
  3. macOS 的 bash 在遇到行尾的 \r 时静默失败 ^[extracted]

症状

Section titled “症状”

\r 在终端中不可见，但 bash 将其解析为命令的一部分 ^[extracted]。pipefail 行实际变成了 set -o pipefail\r，bash 不认识这个选项名。

实际影响

Section titled “实际影响”

AgentMemory 项目的 Mac 端调度任务曾被此问题冻结 6 天，积累了 38 个未处理任务 ^[extracted]。调度器按时触发，脚本启动，但内部 agent 调用全部失败——因为 shell 脚本在启动 agent CLI 前，就连 set -o pipefail 这行都没过去。

根因

Section titled “根因”

Windows 的 git ls-files --eol 显示：6 个 .sh 文件的 index 为 lf，但 worktree 为 crlf / mixed，仓库没有 .gitattributes 且 core.autocrlf=true——这正是产生 CRLF 工作副本的精确条件 ^[extracted]。

⚠️ 即使添加了 eol=lf 的 .gitattributes 属性，也不足以覆盖 core.autocrlf=true 在 checkout 时的行为；必须同时设置 core.autocrlf=false 才能让工作副本真正变成 LF ^[extracted]。

陷阱 2：最小化 PATH

Section titled “陷阱 2：最小化 PATH”

机制

Section titled “机制”

launchd 和 cron 以受限环境运行：

用户本地安装的 CLI——~/.nvm/.../bin、~/.local/bin、Homebrew——全部不可达 ^[extracted]。

症状

Section titled “症状”

“在我终端里能跑”就是陷阱本身——两个 bug 都只在调度/同步的环境中才会暴露，从不在交互式终端中出现，因此所有手动测试都会通过 ^[inferred]。

实际影响

Section titled “实际影响”

AgentMemory Mac 周作业在 2026-06-01T08:00:01 触发，两个 agent 任务均记录 exit code 127，watermark 停滞在 2026-05-27 长达 6 天 ^[extracted]。

为什么这两个陷阱特别危险

Section titled “为什么这两个陷阱特别危险”
特征说明
静默调度器不报错，任务状态显示 “已触发”
延迟发现故障可累积数天到数周才被注意到 ^[inferred]
误导性”在我终端里能跑” 让人误以为一切正常
修复方向易错对 exit-127 重新安装触发器毫无作用——需要修 PATH，不是修调度 ^[inferred]
跨机器扩散一旦 Windows 端产生 CRLF，Syncthing 几秒内就把脏文件传到 Mac ^[extracted]

防御措施

Section titled “防御措施”

详见 跨 OS Git 换行符配置，核心要点：

  1. Day 1 添加 .gitattributes：* text=auto eol=lf，强制 *.sh/*.py/*.json/*.md eol=lf，保留 *.ps1 eol=crlf
  2. Windows 端设置 core.autocrlf=false（.gitattributes 单独不够）
  3. Renormalize 一次：git add --renormalize . 后重新 checkout
  4. 调度作业中固定 PATH：在调用 CLI 的卡口处写绝对路径或显式设置 PATH
  5. 以真实环境测试：env -i PATH=/usr/bin:/bin bash <script> 可同时复现两类问题
  6. 让调度静默失败变成可见信号：非空 tasks/failed/ 或 stagnant watermark 应触发告警

适用范围

Section titled “适用范围”
  • 适用：文件级同步的工作树（Syncthing、Dropbox、iCloud）+ 调度任务
  • 不适用：纯 Git 克隆（每台机器独立 clone，不共享 working tree），因为 Git 在 checkout 时自行应用 EOL 规范化 ^[extracted]
  • 具体的安装路径（~/.nvm、~/.local/bin）是此环境的特例，但用户本地 prefix 对 launchd 不可见的模式是通用的 ^[ambiguous]
