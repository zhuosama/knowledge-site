  1. A3 的题面文档已找到（2026-05-04 复核）

      后文「Anleitung 4.3 要求逐条对照」一节会把每一条 Bearbeitungsschritt 对应到 A3_Timer.c / A3_Timer_it.c 的具体实现位置。

  2. A3_Timer_it.c 的文件头标题写成了“Entprellen”
    它的第一行写的是：

    • Project: Aufgabe3 - Professionelles Entprellen mit Timer 这和 A4 的“Debounce / Entprellen”更像，和 A3 的 Timer 主题不一致。
      但它的中断向量表实际绑定的是：
    • ISR_S0
    • ISR_Timer 所以实际功能仍然是 A3 Timer，不是 A4。这只是注释 typo，不影响功能；如果老师抽查注释可以主动指出。

  3. A2 的讲解结构不再完全适用于 A3 当前代码
    A2 的核心分层是：

    • ISR 只置位 flag
    • 主循环执行整个交通灯流程

    但 A3 当前代码已经变成：

    • ISR_S0() 只负责启动状态机
    • ISR_Timer() 每 1 ms 推进状态
    • 主循环几乎不再执行业务逻辑，只负责 __WFI()

因此，本页会按当前 A3 实际代码来讲，而不是机械沿用 A2 的结构描述。

Vorbereitungsfragen 答案要点

Section titled “Vorbereitungsfragen 答案要点”

来源：Anleitung §4.3 Vorbereitung 列表 a-e。这一节给老师抽查时的口头回答模板。

a. Skriptkapitel zum Timer：参见 SysTick 与定时器，重点是 PSC/ARR 的级联分频公式 f_update = f_clk / (PSC+1) / (ARR+1)。

b. ST 文档 TIM6 关键寄存器：

  • RCC->APB1ENR1 — TIM6EN bit，给 TIM6 上时钟
  • TIM6->CR1 — CEN（启动计数）、URS、UDIS 等控制位
  • TIM6->PSC — 16-bit 预分频
  • TIM6->ARR — 16-bit 自动重装值
  • TIM6->CNT — 当前计数
  • TIM6->EGR — UG bit，强制立即装载 PSC/ARR
  • TIM6->SR — UIF（update interrupt flag）
  • TIM6->DIER — UIE（update interrupt enable）

c. Prescaler 计算：

选 PSC = 1599（除以 1600 → 10 kHz），ARR = 9（除以 10 → 1 kHz）。
启动顺序：先配 RCC、PSC、ARR、EGR=UG、SR=0、DIER=UIE，再 NVIC_EnableIRQ，最后 CR1 |= CEN。

d. Timer 相对 delay() 的优势：

  1. CPU 不被占用，可以 __WFI() 进入 sleep，能耗显著降低
  2. 时间精度由硬件保证，不受其他代码执行长度影响
  3. 多任务并行：行人阶段同一个 timer 同时维护「总剩余 15 s」和「蓝灯每 500 ms 翻转」两套节奏
  4. 中断响应时延确定，可与其他高优先级中断协同

e. Flussdiagramm：本页「代码总体流程」一节用 4 条事件链（上电、按钮、timer tick、行人阶段）覆盖，可在抽查时直接照念。完整可视化版本见 A3_Flussdiagramm.jpg（与本笔记同目录），含 4 个集群：

  • main() — 初始化序列 + __WFI() 主循环
  • ISR_S0() — EXTI0 下降沿 → 状态机启动判断
  • ISR_Timer() + Traffic_timer_tick() — TIM6 update → UIF 清除 → 计时递减 → 行人阶段双时间分支
  • Traffic_advance() 状态机 — 7 个阶段的转移关系，含每阶段的 LED 与时长

虚线箭头表示中断触发关系（__WFI 被 EXTI0 / TIM6 唤醒），点线箭头表示对 g_traffic_state 的写入。

任务目标

Section titled “任务目标”

A3 的目标不是再改“按钮怎么触发”，这一点在 A2 已经完成了。
A3 真正新增的是：

  • 把 A1/A2 里的 busy-wait 延时改成硬件 timer 驱动
  • 让 CPU 不再靠空转循环等待时间过去
  • 让交通灯流程按“状态 + 剩余时间”推进

一句话概括：

A2 是“按钮触发方式升级”，A3 是“等待方式升级”。

本任务新增的思路

Section titled “本任务新增的思路”

1. 时间不再靠 CPU 空转，而靠 TIM6 提供节拍

Section titled “1. 时间不再靠 CPU 空转，而靠 TIM6 提供节拍”

A1/A2 里的 delay() 本质是：

  • CPU 一直执行空循环
  • 什么都不做
  • 只是为了“把时间熬过去”

A3 改成：

  • TIM6 每隔 1 ms 产生一次 update event
  • CPU 进入休眠
  • 只有 timer 中断到来时才醒一下，处理“还剩多少时间、要不要切换下一相位”

这就是 A3 里“Professionelles Warten”的核心含义：
等待这件事交给硬件 timer，而不是交给 CPU 空转。

2. A3 不再是“顺着一段大流程跑到底”

Section titled “2. A3 不再是“顺着一段大流程跑到底””

A2 的主循环可以写成：

  • 等按钮
  • 绿灯等 10 秒
  • 黄灯 1 秒
  • 红灯 1 秒
  • 蓝灯闪 15 秒
  • …

这种写法的问题是：
它依赖“我现在就把这一整段流程连续执行完”。

但 A3 用 timer 后，每次中断只过了 1 ms。
因此程序不能再“从头跑完整段流程”，而必须回答两个问题：

  1. 我现在处于哪个阶段？
  2. 这个阶段还剩多少时间？

所以 A3 引入了：

  • traffic_state_t
  • g_traffic_state
  • g_state_timeout_ms

这说明 A3 已经从“顺序脚本式流程”走向“状态机式流程”。

3. A3 的分工不再是 A2 那种“ISR 触发、main 执行业务”

Section titled “3. A3 的分工不再是 A2 那种“ISR 触发、main 执行业务””

A3 当前代码的真实分工是：

  • ISR_S0()：只负责启动序列
  • ISR_Timer()：负责按毫秒推进序列
  • main()：负责睡眠等待中断

这就是本题最容易卡住的地方。
如果你还按 A2 的思维去看，会误以为“主循环会处理交通灯流程”，但 A3 已经不是这样了。

4. 蓝灯闪烁不能只靠一个总时间变量

Section titled “4. 蓝灯闪烁不能只靠一个总时间变量”

行人阶段有两个同时存在的时间逻辑：

  1. 整个行人阶段总共持续 15 秒
  2. 蓝灯每 500 ms 翻转一次，形成 1 Hz 闪烁

所以 A3 不是只多了一个“总剩余时间”，而是多了两层时间：

  • g_state_timeout_ms 当前阶段总剩余时间
  • g_blue_toggle_ms 距离下一次蓝灯翻转还剩多少毫秒

这就是为什么 A3 比 A2 多出一组专门管理“阶段内局部节奏”的变量。

本任务新增的语法 / 寄存器 / 机制

Section titled “本任务新增的语法 / 寄存器 / 机制”

traffic_state_t 是什么，为什么要先定义它

Section titled “traffic_state_t 是什么，为什么要先定义它”

A3 先定义了一个枚举类型：

这不是一个变量，而是一个类型定义。
它的作用是：给“交通灯当前处于哪个阶段”提供一组有名字的常量。

如果不用它，只写整数：

  • 0
  • 1
  • 2
  • 3

老师一问“2 是什么意思”，你就很难讲。
但现在你可以直接说：

  • TRAFFIC_STATE_WAIT_RED 就是“当前处于红灯 1 秒阶段”

TIM6 为什么会在 A3 出现

Section titled “TIM6 为什么会在 A3 出现”

TIM6 是 STM32 的通用定时器之一。
在 A3 里，它被拿来做最简单但很关键的一件事：

  • 每 1 ms 触发一次 update interrupt

这样程序就有了统一时间基准。
之后所有“等 10 秒”“等 1 秒”“500 ms 翻转一次”都变成：

  • “计数多少个 1 ms tick”

6. TIM6->EGR = TIM_EGR_UG;

  • 作用：DMA/Interrupt Enable Register
  • 改动 bit：UIE = Update Interrupt Enable

含义是：

  • 允许“update event”产生中断请求

如果少了这句，即使计数到了 ARR，CPU 也不会因为 update event 进入 ISR_Timer()。

Section titled “9. NVIC_SetPriority(TIM6_DAC_IRQn, 2);”

这是把 TIM6 中断优先级设成 2。
当前代码里 EXTI0 是优先级 1，TIM6 是优先级 2，表示：

  • 按钮触发中断优先级更高一点
  • timer tick 稍低一点

Section titled “10. NVIC_ClearPendingIRQ(TIM6_DAC_IRQn);”

清掉 TIM6 在 NVIC 层面的 pending 状态。

11. NVIC_EnableIRQ(TIM6_DAC_IRQn);

Section titled “11. NVIC_EnableIRQ(TIM6_DAC_IRQn);”

真正允许 CPU 响应 TIM6 的中断请求。

注意这里和 A2 一样，还是两层：

  • 外设层：TIM6->DIER 允许发请求
  • NVIC 层：NVIC_EnableIRQ(...) 允许 CPU 接收请求

12. TIM6->CR1 |= TIM_CR1_CEN;

Section titled “12. TIM6->CR1 |= TIM_CR1_CEN;”
  • 操作寄存器：TIM6->CR1
  • 改动 bit：CEN = Counter Enable
  • 硬件效果：启动 TIM6 计数器

只有到这句之后，TIM6 才真正开始跑。

代码总体流程

Section titled “代码总体流程”

这一节必须按“事件链”来理解，不能只按文件顺序看。

1. 上电后的初始化链

Section titled “1. 上电后的初始化链”

程序启动后，main() 顺序执行：

  1. __disable_irq()
  2. GPIO_init()
  3. Timer_init()
  4. Traffic_state_enter(TRAFFIC_STATE_IDLE_GREEN)
  5. __enable_irq()
  6. 进入 for(;;) { __WFI(); }

这里的关键点是：

  • GPIO 和 EXTI 保留了 A2 的按键触发能力
  • 新增 TIM6 作为 1 ms 时间基准
  • 初始状态明确设为 IDLE_GREEN

2. 按钮按下后的执行链

Section titled “2. 按钮按下后的执行链”

按钮按下时，事件链是：

  1. PB0 从 High 变 Low
  2. EXTI0 检测到下降沿
  3. NVIC 允许 CPU 响应 EXTI0_IRQn
  4. CPU 进入 ISR_S0()
  5. ISR_S0() 发现当前在 TRAFFIC_STATE_IDLE_GREEN
  6. 调用 Traffic_state_enter(TRAFFIC_STATE_WAIT_GREEN)
  7. 当前状态变成“绿灯等待 10 秒阶段”
  8. 中断返回
  9. CPU 回到 __WFI() 等下一次中断

注意：
按钮中断没有直接推进完整流程，它只是把状态机推到第一阶段。

3. timer 每 1 ms 推进一次的执行链

Section titled “3. timer 每 1 ms 推进一次的执行链”

只要 TIM6 在运行，就会不断发生 update event：

  1. TIM6 计数到 ARR
  2. 产生 update event
  3. UIF 置位
  4. 若 UIE 已开，则向 NVIC 发出中断请求
  5. CPU 进入 ISR_Timer()
  6. ISR_Timer() 清 UIF
  7. 调用 Traffic_timer_tick()
  8. Traffic_timer_tick() 递减当前时间，必要时调用 Traffic_advance()
  9. Traffic_advance() 决定进入下一阶段
  10. Traffic_state_enter() 装载下一阶段的 LED 和时间

这条链才是 A3 的主体。

4. 行人阶段为什么更特殊

Section titled “4. 行人阶段为什么更特殊”

行人阶段不只是“等 15 秒”，而是同时做两件事：

  1. 15 秒总阶段倒计时
  2. 每 500 ms 翻转一次蓝灯

所以 Traffic_timer_tick() 在 TRAFFIC_STATE_PEDESTRIAN 这个分支里会：

  1. 先减总时间 g_state_timeout_ms
  2. 再减蓝灯翻转时间 g_blue_toggle_ms
  3. 如果 g_blue_toggle_ms == 0
    • 翻转 g_blue_led_on
    • 重新装载 BLUE_TOGGLE_MS
    • 重写 LED mask
  4. 如果 g_state_timeout_ms == 0
    • 行人阶段结束，进入下一状态

5. 为什么主循环几乎没有业务逻辑

Section titled “5. 为什么主循环几乎没有业务逻辑”

因为 A3 的真实业务行为已经分散到：

  • 外部事件启动：ISR_S0()
  • 时间推进：ISR_Timer()
  • 状态切换：Traffic_advance()
  • 状态装载：Traffic_state_enter()

所以 main() 不再像 A2 那样“手里握着完整流程”，它只是系统壳子。

关键改动总结

Section titled “关键改动总结”

相对于 A2，A3 的关键变化可以概括成 6 点：

  1. 删除了 A1/A2 那种基于 delay() 的 busy-wait 时序推进思路
  2. 新增 TIM6 作为 1 ms 时间基准
  3. 新增 traffic_state_t 和 4 个状态变量，正式进入“状态机式实现”
  4. 主循环从“等待 flag 并执行业务”变成“只做 __WFI()”
  5. 交通灯时序推进主体从 main() 转移到 ISR_Timer()
  6. 行人蓝灯闪烁通过“总阶段时间 + 局部翻转时间”双计时实现

一句最重要的总结：

A2 是 interrupt 触发业务，A3 是 timer 驱动业务推进。

老师可能追问的问题与回答

Section titled “老师可能追问的问题与回答”

为什么 A3 还保留 ISR_S0()，不直接全靠 timer？

Section titled “为什么 A3 还保留 ISR_S0()，不直接全靠 timer？”

因为 timer 只负责“时间流逝”，不能自己知道“用户什么时候按了按钮”。
所以：

  • ISR_S0() 负责接收外部事件
  • ISR_Timer() 负责处理时间事件

两类事件分工不同，不能互相替代。

为什么不用 A2 那样的主循环 + flag + delay()？

Section titled “为什么不用 A2 那样的主循环 + flag + delay()？”

因为那样本质还是 CPU 空转等待。
A3 的目标就是把“等待”交给硬件 timer，让 CPU 休眠，只在中断到来时处理状态。

为什么要用状态机，不直接写一连串 if / delay？

Section titled “为什么要用状态机，不直接写一连串 if / delay？”

因为 timer ISR 每次只过了 1 ms。
程序必须知道：

  • 自己现在在哪个阶段
  • 这个阶段还剩多久

这正是状态机擅长解决的问题。

为什么蓝灯要单独再加 g_blue_toggle_ms？

Section titled “为什么蓝灯要单独再加 g_blue_toggle_ms？”

因为“行人阶段总共 15 秒”和“蓝灯每 500 ms 翻转”是两个不同节奏。
只用一个变量无法同时表达：

  • 阶段总剩余时间
  • 阶段内部闪烁节奏

为什么主循环只剩 __WFI() 反而是更好的设计？

Section titled “为什么主循环只剩 __WFI() 反而是更好的设计？”

因为这说明：

  • 事件驱动路径已经建立完整
  • CPU 不需要无意义空转
  • 主循环不再承担本不属于它的时间管理工作

TIM6->EGR = TIM_EGR_UG; 为什么不能省？

Section titled “TIM6->EGR = TIM_EGR_UG; 为什么不能省？”

因为它用于强制产生一次 update generation，让刚写进去的预分频和重装值立即装载。
如果你不写，timer 的配置生效时机可能不如你预期稳定。

Section titled “1. 中断优先级故意把 EXTI0 设得比 TIM6 高”

ARM Cortex-M 数值越小优先级越高，所以 EXTI0 > TIM6。后果：

  • TIM6 不能抢占 EXTI0，所以 Traffic_state_enter() 在 ISR_S0 中执行时，对 4 个 volatile 变量的连写是天然原子的，不需要加 __disable_irq() 保护。
  • 反过来如果 EXTI0 在 TIM6 ISR 执行中触发，TIM6 ISR 会被打断；但 ISR_S0 只读一次 g_traffic_state 并仅在 IDLE 时切换，不会破坏 timer tick 的递减逻辑。

2. ISR_S0 天然防抖（针对启动事件）

Section titled “2. ISR_S0 天然防抖（针对启动事件）”

按钮抖动会在按下瞬间产生多次下降沿，每次都会进入 ISR_S0()。但：

第一次抖动后 g_traffic_state 已经不是 IDLE_GREEN，后续抖动进入 ISR 后什么都不做，只清 pending bit。所以 A3 不需要 A4 的 timer 去抖也能正确启动序列。这一点是 A3 → A4 过渡的天然铺垫：A4 才需要正式去抖，因为 A4 引入了「按下次数计数」语义，每一次下降沿都有意义。

3. TIM6 SR 清零方式与 EXTI PR1 不同

Section titled “3. TIM6 SR 清零方式与 EXTI PR1 不同”

两个寄存器的清除语义在 STM32 参考手册里就不一样：

  • TIM SR 是「写 0 清除」（rc_w0），所以读-改-写把 UIF 那一位写 0 是对的。
  • EXTI PR1 是「写 1 清除」（rc_w1），所以直接 = (1<<0) 是对的。

绝对不能交叉混用，否则要么清不掉、要么把别的位也意外清掉。这是 A3 老师抽查时很爱问的细节。

4. 行人阶段的「双时间」节拍如何不互相冲突

Section titled “4. 行人阶段的「双时间」节拍如何不互相冲突”

Traffic_timer_tick() 在 TRAFFIC_STATE_PEDESTRIAN 分支里的执行顺序是：

  1. 先递减 g_state_timeout_ms
  2. 判断 g_state_timeout_ms == 0 → 直接 Traffic_advance() 跳出，不再翻转蓝灯
  3. 否则递减 g_blue_toggle_ms
  4. 判断 g_blue_toggle_ms == 0 → 翻转 g_blue_led_on 并重装

这个顺序保证：阶段结束的那一 ms 不会再多翻一次蓝灯，也不会让蓝灯停在中间状态——后续的 WAIT_RED_AFTER_BLUE 会立刻把 LED mask 重写为只有红灯。

5. 启动顺序：为什么 Traffic_state_enter(IDLE_GREEN) 要放在 __enable_irq() 之前

Section titled “5. 启动顺序：为什么 Traffic_state_enter(IDLE_GREEN) 要放在 __enable_irq() 之前”

Timer_init() 末尾 CR1 |= TIM_CR1_CEN 已经让 TIM6 开始计数，但全局中断还被 __disable_irq() 屏蔽，所以 UIF 即使置位也不会进入 ISR_Timer()。等到 __enable_irq() 后，TIM6 ISR 第一次被允许执行时看到的状态已经是 IDLE_GREEN（Traffic_timer_tick() 直接 return），因此不会出现「初始化中途被 timer 中断打断、状态机半装载」的竞争。
