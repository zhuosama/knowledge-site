A4 Debounce 低功耗变体讲解

A4 Debounce 低功耗变体讲解

Section titled “A4 Debounce 低功耗变体讲解”

本页是 A4 Debounce 讲解 的延伸笔记，主版本（1 ms tick + Countdown 去抖）的全部内容默认已掌握。这里只讲为什么再优化、怎么优化、新增了哪些寄存器/语法/链接技巧。也建议先读 A3 Timer 低功耗变体讲解——本变体把 A3 lowpower 的两条思路（IDLE 停 timer / OPM phase timer）原封迁移到 A4，再加一条新的（OPM 去抖）。

问题背景

Section titled “问题背景”

A4 主版本沿用了 A3 的 1 ms TIM6 tick，原因是：debounce 倒计时和 Ampel 倒计时都可以共用一个 1 ms 时基，省一个 timer。功能上完全满足 Anleitung 4.4。

但教授在 A3 课堂讨论时已经点出：「professionelles Warten」的意思不是 timer 替代 busy-wait，而是CPU 只在该醒的时刻醒。把 A3 的两条 lowpower 优化思路应用到 A4，本来唤醒次数应该再降一个数量级；而 Anleitung 4.4 的 Tipp 直接给出了第三条 lowpower 思路：

„Tipp: speziell zum Entprellen bietet sich eine Funktion der meisten Timermodule in den ST-Prozessoren an: der One Pulse Mode (OPM-Bit im CR1).”

把这三条放在一起，就是 A4 的低功耗参考实现。

Section titled “三条 lowpower 思路并用”
思路来源作用
Ansatz 1：IDLE → TIM6 停A3 lowpower等按钮期间 0 wakeups/s
Ansatz 2：每阶段 OPM/periodic 重配 TIM6A3 lowpower普通阶段 1 wakeup/阶段，行人 30 wakeups
Ansatz 3：TIM7 OPM 30 ms 当 debounceAnleitung 4.4 Tipp每次按键 1 wakeup（30 ms 后解锁）

2. __attribute__((weak)) —— 给共享 it.c 的弱回退实现

Section titled “2. __attribute__((weak)) —— 给共享 it.c 的弱回退实现”

主版本 A4_Entprellen.c 不使用 TIM7，lowpower 版本 A4_Entprellen_lowpower.c 使用 TIM7。两个版本共享同一个 A4_Entprellen_it.c（里头放着中断向量表）。如果 vector 表静态引用 ISR_DebounceTimer，那么链接主版本时会因找不到符号而失败。

解决办法：在 it.c 里给 ISR_DebounceTimer 一个 weak fallback：

__attribute__((weak)) 是 GCC 扩展，意思：

  • 这个符号默认存在（链接器找得到）
  • 但是任何非 weak 的同名符号都会优先 override 它

lowpower.c 里写的是普通定义 void ISR_DebounceTimer(void) { ... }，是强符号——链接 lowpower 时强符号顶掉弱符号，weak fallback 不被链接进二进制；链接主版本时找不到强符号，weak fallback 被链接，但 TIM7 从未被启用，所以 fallback 永远不会真的执行。

这是 GCC/CMSIS 项目里给 HAL ISR 留 hook 的标准技巧，CMSIS startup 文件里所有 Default_Handler 别名也用同一机制。

4. 单一全局 lockout vs 每个按键独立 lockout

Section titled “4. 单一全局 lockout vs 每个按键独立 lockout”

A4 主版本有两个独立 counter：g_s0_debounce_ms 和 g_s1_debounce_ms，S0 按下后 30 ms 内 S1 仍可独立按。

lowpower 版本只有一个 timer (TIM7) + 一个 flag g_debounce_locked：S0 按下后 30 ms 内 S1 也被忽略。设计权衡：

  • 优点：单 timer 资源，状态简单
  • 代价：极端场景下 S0 按下 5 ms 后 S1 按下会被吞掉

但在 A4 题目语境下这没有实际影响——4.4 题面里 S1 只用于 replace 模式确认，replace 模式下 S0 反正被忽略，所以两键 30 ms 内”同时”按的物理场景不在题面内。

如果将来需要两键独立去抖，方案是再开一个 timer（比如 TIM15/TIM16/TIM17 之一）给 S1 专用。

老师可能追问的问题

Section titled “老师可能追问的问题”

为什么不直接修改 A4 主版本，要保留两份？

Section titled “为什么不直接修改 A4 主版本，要保留两份？”

工程上保留两个并行实现的理由：

  1. 教学对比：把”1 ms tick 通用方案 vs 真正 lowpower 方案”放一起，差异一眼可见
  2. 风险隔离：主版本是已经通过验证、能直接交作业的实现；lowpower 是优化变体，开发期间出 bug 不会影响交作业
  3. 题目语义不要求 lowpower：Anleitung 4.4 没说”必须最低功耗”，OPM 只是 „Tipp”。主版本是题目的正解；lowpower 是把 Tipp + A3 lowpower 思想合并后的进阶版

为什么 TIM7 不直接走 TIM6 的同一个向量？

Section titled “为什么 TIM7 不直接走 TIM6 的同一个向量？”

TIM6_DAC_IRQn (IRQ 54) 和 TIM7_DAC_IRQn (IRQ 55) 是两条独立的 NVIC 线，硬件层面就分开——TIM7 溢出根本不会让 CPU 跳到 ISR_Timer，会直接跳到向量表第 55 项指向的 ISR_DebounceTimer。

更精确的派单链：

TIM6 和 TIM7 触发互不干扰，没有”广播给所有 ISR”这种概念。如果硬把 TIM7 接到 TIM6 的 ISR 上，需要在 ISR 里多读一次 TIM7->SR.UIF 判断到底是谁触发，反而更绕。

详见 语法总表 · 中断号 / 向量表 / ISR 派单机制——那里完整讲了”NVIC 怎么按 IRQ 号查表派单”以及”共享 IRQ 号（TIM6_DAC、TIM7_DAC）为什么 ISR 里要查 SR.UIF”。

__attribute__((weak)) 是 GCC 扩展，可移植吗？

Section titled “__attribute__((weak)) 是 GCC 扩展，可移植吗？”

ST 官方 startup 文件和 CMSIS 头文件就大量用 weak（Default_Handler 的所有别名都是 weak）。STM32 工具链默认就是 ARM GCC，所以这个写法在 STM32CubeIDE 项目里是标准做法。如果换成 Keil/IAR，对应的关键字分别是 __attribute__((weak))（Keil 5+）和 #pragma weak（IAR），语义相同。

30 ms 内 S1 也被锁住，会不会违反 Anleitung？

Section titled “30 ms 内 S1 也被锁住，会不会违反 Anleitung？”

Anleitung 4.4 的 c. 说「Um jeden einzelnen Tastendruck eindeutig festzustellen, wird hier ein Entprellen benötigt」——目标是”每次按下唯一被识别”，没说两键必须独立去抖。物理上人不会在 30 ms 内一手按 S0 一手按 S1，所以两键共享一个 30 ms 锁定窗口在实际使用中等效。

如果题目改成「替换 LED 时 S0 和 S1 都可能在 30 ms 内被触摸到」，那就需要两个独立 timer。可以用 TIM15/16/17 任一个补一个 OPM 给 S1。

TIM6 在 PEDESTRIAN 和 Replace 都跑 periodic，区别是什么？

Section titled “TIM6 在 PEDESTRIAN 和 Replace 都跑 periodic，区别是什么？”

只是 ARR 和 ISR 路径不同：

阶段TIM6.ARRISR 内做什么
PEDESTRIAN499 (500 ms)翻 BLUE + --g_pedestrian_toggles_left，到 0 时 Traffic_advance()
Replace249 (250 ms)翻 RED，永远循环（直到 S1 退出）

进入新阶段时只需要重新调一次 Phase_timer_start_periodic(ms)，这个函数会先停 TIM6，再写新 ARR，再开 — 切换是无缝的。

为什么 lowpower.c 自己定义 ISR_DebounceTimer 时不能写 __weak？

Section titled “为什么 lowpower.c 自己定义 ISR_DebounceTimer 时不能写 __weak？”

如果 lowpower 这边也是 weak，链接器看到两个 weak 符号会随机选一个（实现定义行为），可能选 it.c 的空 fallback——TIM7 触发后 g_debounce_locked 永远不被清零，整个去抖机制坏掉。所以：

  • it.c 里的 fallback：weak
  • lowpower.c 里的真实实现：强符号（普通定义）

强符号永远 override weak 是 ELF 链接器的硬规定，行为确定。

为什么 IDLE 状态停 TIM6 还需要 Phase_timer_stop() 显式清 NVIC pending？

Section titled “为什么 IDLE 状态停 TIM6 还需要 Phase_timer_stop() 显式清 NVIC pending？”

防御性写法。考虑这种时序：

  1. TIM6 已经计数到 ARR 触发 update event，UIF=1
  2. ISR 还没进，新事件让我们想 Traffic_state_enter(IDLE_GREEN)
  3. 如果只清 CR1.CEN，UIF 和 NVIC pending 还在
  4. 退出 Phase_timer_stop() 后下一行可能立刻 enable IRQ，进了一次”不该有的” ISR

SR &= ~UIF 加 NVIC_ClearPendingIRQ 把残留信号都扫掉，保证下次启动 TIM6 是个干净状态。

本变体中最容易看不懂的代码逐句解释

Section titled “本变体中最容易看不懂的代码逐句解释”

1. __attribute__((weak)) 加在函数定义上是什么意思

Section titled “1. __attribute__((weak)) 加在函数定义上是什么意思”

__attribute__((weak)) 不影响函数本身的代码，只影响这个符号在链接器眼里的优先级：

  • 普通定义：强符号（strong）。链接器看到两个同名强符号会直接报 multiple definition 错误
  • weak 定义：弱符号。链接器看到强符号 + 弱符号时默默选强符号，弱定义连同函数体一起被丢弃

所以这个空函数体只在「lowpower.c 不在 build 里」时才会被链接进二进制。

2. Debounce_timer_start() 中为什么要重写 ARR

Section titled “2. Debounce_timer_start() 中为什么要重写 ARR”

理论上 Timer_init() 里已经写过一次了，TIM7 的 ARR 是 29。但是为了 防御性 + 可读性，每次启动 OPM 都把 ARR 显式写一遍：

  • 万一别处误改了 TIM7 配置，重写 ARR 把它恢复
  • 代码读起来”启动一次 30 ms”是自包含的，不需要回头查 init

代价只有 1 条 MMIO 写，几个时钟周期。

3. g_debounce_locked 为什么不区分 S0 / S1

Section titled “3. g_debounce_locked 为什么不区分 S0 / S1”

主版本是两个独立 counter，本变体合并成一个 flag。原因有三：

  1. 题目语义不要求独立去抖
  2. 一个 TIM7 同时只能为一个 30 ms 计时
  3. 即便都用一个 lockout，30 ms 后 TIM7 OPM 触发清 flag，下一次 ISR_S0 或 ISR_S1 都能继续工作——只要不在同一个 30 ms 内一起按

合并后代码更短，状态空间更小，更容易讲清楚。

4. 为什么 Phase_timer_start_periodic() 既被 PEDESTRIAN 又被 Replace 用

Section titled “4. 为什么 Phase_timer_start_periodic() 既被 PEDESTRIAN 又被 Replace 用”

两段代码共用同一个 helper，但 ms 参数不同：

  • PEDESTRIAN → 500
  • Replace → 250

helper 本身不关心是哪段在用，只负责”按 ms 周期触发 TIM6”。 ISR 里靠 g_replace_mode 和 g_traffic_state 区分该做什么。这是 lowpower 实现里少有的「资源共享」点，避免代码膨胀。

如何切换两个版本编译

Section titled “如何切换两个版本编译”

工程里同时存在 A4_Entprellen.c 和 A4_Entprellen_lowpower.c 时会因为重复符号（main、ISR_S0、ISR_S1、ISR_Timer）链接失败。本仓库默认通过 .cproject 的 excluding="A4_Entprellen_lowpower.c" 把 lowpower 文件默认排除，Debug + Release 两份 build configuration 都不会编它。

要切换到 lowpower：

  1. STM32CubeIDE → 右键 A4_Entprellen.c → Resource Configurations → Exclude from Build → 勾上 Debug + Release
  2. 右键 A4_Entprellen_lowpower.c → Resource Configurations → Exclude from Build → 取消勾选
  3. Clean Build

或者直接改 Debug/Src/subdir.mk，把 A4_Entprellen.c 换成 A4_Entprellen_lowpower.c（但 IDE 重启可能 regenerate 把改动丢掉，不推荐）。

老师抽查时如果切换演示，记得提前确认链接通过、并把 lowpower 上板跑过一次。
